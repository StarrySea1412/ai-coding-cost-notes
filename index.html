AI 编程省钱的另一半

上下文怎么压、习惯怎么改、模型怎么选——上半场已经有很多人讲过了。这篇写账单的另一半：渠道的生死、标价之外的成本、探测的纪律，和一条能救命的降级链。全部来自我自己的实测记录。

约 25 分钟 5 章 · 1 张清单 更新于 2026.10.14

如果你已经把上下文压得很小、把会话分得很清、把模型选得很准——恭喜，上半场你已经做对了。但把账单真的拆开看，还有一半的钱，花在方法论管不到的地方：某个渠道昨晚静静地死了；某个模型预扣了验证金、却没出结果；某次中断让整个任务从头再来。

这一半不写在提示词里，写在供给层里。这篇手记只讲这一半：怎么发现渠道在死、怎么算清标价之外的成本、怎么安全地探测、怎么让产出不押在任何单一渠道上。

文中所有渠道、服务商、域名均已匿名化处理；全部数字来自本地探测与真实任务的记录。探测请仅针对你已付费或获得授权的服务。

01

SILENT DEATH

渠道会死，而且是静默的

服务商不会给你发讣告。它只是某一天开始不再接活——而这一切，通常发生在你已经把工作流挂上去之后。

实测 · 2026.10

先讲一个今天下午刚刚发生的事。我买了一个新渠道，配好之后做例行验证：模型列表一切正常，文本模型在，生图全系都在。第一张真实图片发出去——503。错误码很短：no_available_account，"没有可用的账号"。

这个错误值得停下来看一眼。它说的不是你配错了钥匙，不是参数不对，也不是你被限流——端点活着（空参数请求会被正常地参数校验拒掉），认证正常，断掉的是它自己的上游供给：它没货了。遇到这种错误，正确的动作只有一个：立刻切备用渠道。反复重试是最亏的动作，它既不改变供给，也在消耗你的时间。

渠道的五种死法

这两年我见过、也亲自踩过的死法，基本逃不出这五类。认识它们，是为了在看到错误码的那一秒就知道该干什么。

DEATH 01连接层死

域名不通、TLS 握手都完不成。最诚实的一种死法，一眼可见。

DEATH 02门禁层死

钥匙被清，401 / 403。干脆利落——但你如果只有一个渠道，它就是灭顶之灾。

DEATH 03计费层死

验证金照扣，活不干，超时收场。最伤钱包：失败还不一定留痕。

DEATH 04供给层死

端点全活、上游无号——就是今天遇到的那一种。最容易被误判成"自己的问题"。

DEATH 05 · 最危险慢性死

时好时坏，成功率缓慢雪崩。没有明确的死亡时刻，只有越来越多的"偶尔失败"——等你注意到它时，效率已经掉了一个月。

一张会让渠道现原形的体检单

既然死法是静默的，定期体检就得靠真实的成功率，而不是"能不能连上"。我给自己维护的渠道池做了一张体检单，每周跑一次最小任务，只记录事实：

渠道体检单

WEEKLY CHECKUP · 最小真实任务
站 A在用今日验证通过 · 延迟正常
站 B观察期昨天一次超时，待复测
站 C疑似断供今日首图 503 · 无可用账号
站 D已死两周前失联，不再重试
列表 ≠ 可用记录的是最小真实任务的成败，不是"能不能连上"

模型列表，是服务商最愿意保活的东西——它便宜、无状态，还能当广告。所以"列表里有"是必要而不充分条件：看菜单不算体检，点一道菜看它上不上桌，才算。

把渠道当库存管理，而不是当工具管理：它有存活率、有库存深度、有补货周期。你不需要知道每家为什么死，你只需要比你的工作流更早知道。

02

HIDDEN COSTS

标价的另一面：三种隐形成本

上半场的省钱文章会告诉你"这个模型每百万 token 多少钱"。但那个数字是标价，不是成本。

账单之外

真实成本要算三个标价里看不到的因子。它们的作用方式各不相同，但方向一致——都在把标价往上抬：

EQUATION · 有效成本

有效成本 ≈ 标称单价 × 重试系数 ÷ 存活率 ＋ 预扣占用

重试系数 ≥ 1，存活率 ≤ 1。两个因子，一个乘、一个除——都让标价变贵。

预扣税

一些服务商对高价模型会预扣验证金，1 到 2 美元级别，用来防刷。失败不退，或者延迟退。它带来的后果很隐蔽：你的余额是"名义余额"。连续试三个贵模型，六美元就先冻在途——而你清单上看到的只是"失败了几次"。所以，试错贵模型之前先看可用余额，比研究官方定价有用得多。

重试税

失败不只是那一次调用的钱。一次中断，意味着上下文重新组织、任务从头再来、注意力重新加载。所以重试成本要乘进总账，而不是加进去：把一个长任务挂在成功率九成的渠道上，省下的单价，会以重跑的次数量级还回去。

信任税（最贵的一项）

一个渠道静默死过一次，你就再也不敢把长任务挂上去。表面上什么都没发生，实际上你的产出速度降了一档。这项成本永远不会出现在账单上——账单只记录花出去的钱，不记录没能产出的时间。

同一件事的两种记法
账单看得见账单看不见
成功的调用费用失败与重试的调用
标称单价预扣冻结在途的余额
token 用量排查静默死亡的那些晚上
月末总计"花了多少""有多少没产出"

自测题：你的主力渠道如果今晚死掉，明天的产出会掉多少？如果这个答案让你不安，说明你还欠一条降级链——第四章见。

03

DISCIPLINE

探测纪律：像专业人士一样验证渠道

验证渠道这件事本身有风险。我踩过最深的一个坑，就是"图快"。

翻车实录

早期我图快，对着一个站点在 60 秒内连发了 5 个不同模型的请求。结果不是 5 个答案，而是一个封禁：IP 被风控直接拉黑，并且没有自动解除。教训浓缩成三条——一次只对一个站说话；主动把节奏降下来；动手之前先估请求量。

现在我的探测有两套刹车。节奏上：同站 ≥ 15 秒间隔、每分钟不超过 4 次，渠道之间严格串行，同一渠道没返回之前不发下一个请求。规模上：测试前先估这次要打多少请求，超预算就先改方案再动手，而不是"先跑了再说"。连续失败也会自动停手——"停下来"是默认行为，不是人肉判断。

黄金三步：从最便宜的问到最贵的问

验证一个新渠道，我固定按三步走。前两步完全免费，几分钟就能把死渠道筛掉；真正花钱的第三步，只留给筛选后的候选：

STEP 1 · 免费

列表探活

一次 GET /models。能返回不等于能用，但不能返回一定不能用——30 秒内排除连接层和门禁层的死法。

STEP 2 · 免费

最小请求

一个空参数的 POST。返回 422 / 400（参数校验错误）＝端点活着；直接 503 no_available_account＝没货，到此为止，不再浪费请求。

STEP 3 · 要花钱

真实任务

一张最小的图、一次最短的补全。拿到产物，才叫"验证过"——这一步是唯一算数的。

冷却纪律

遇到限流和拒绝，差别不在"要不要等"，而在"等多久、之后怎么办"。我的表是这样定的：

403至少冷却 30 分钟，期间不再碰这个站——通常意味着你已经越线了。
429冷却几分钟起步，之后降速试用；还拒绝就再降一档。
401停下来想清楚。通常是钥匙或权限问题——重试一百次，结果一样。
连续失败自动停手。把"停下来"做成默认行为，而不是靠人肉盯。

探测的目的是获取信息，不是证明渠道"能行"。带着这个心态，你会发现大部分验证在前两步就结束了——而且一分钱没花。

04

FALLBACK

别把产出押在一个渠道上：降级链

第一章那家 503 的服务商，还有下半段故事。

实战回放

主力渠道返回 503 的同一秒，任务按候选队列切到了备用渠道。大约两分钟后，图成了。站在使用的视角，今天只发生了一件小事——出图慢了一点。这就是降级链存在的全部意义：让渠道的死亡，变成产出侧一次无关痛痒的延迟。

三个设计原则

  1. 候选要有顺序逻辑

    按质量优先 / 成本优先 / 稳定优先分组排序，不随机抽签。"主力失败时切给谁"是设计好的，不是碰运气。

  2. 分清哪些错误该降级

    超时、5xx、无可用账号 → 降级；401 / 402 / 403 → 立即停。钥匙和余额的问题，换渠道是掩耳盗铃——只会把同一个错误，放大成多个渠道的错误。

  3. 全程留痕

    每一步"为什么切、切到哪、结果如何"都要能回看。黑盒降级遇到事故就是灾难：你连自己切过几次都说不清。

落到配置上大概是这样一张表——主力在前，备选按条件触发，认证类错误直接熔断：

候选队列配置（示例）
# 生图任务的候选队列（示例）
image:
  primary:   { id: chan-a, mode: quality }   # 主力：质量优先
  fallbacks:
    - { id: chan-b, mode: cost,   on: [timeout, 5xx, no_account] }
    - { id: chan-c, mode: stable, on: [timeout, 5xx] }
  abort_on:  [401, 402, 403]                 # 钥匙/余额问题，直接停
  trace:     true                            # 每次切换都留痕

协议差异，要被适配层吃掉

同样是"生图"这一个动作，协议层的返回格式可以完全不同：有的服务返回 data URL，有的返回 markdown 链接，有的连标准端点都不支持、只能走对话式接口兜底。适配层存在的意义，就是把这些差异吃掉——上层只认两种结果：成品，或者失败。你的业务代码不应该知道"第三家渠道的返回格式有点怪"这种事。

这篇手记里那张成品插图，就是这条链跑出来的：主力 503，备用接手，全程留痕。写文章的当天下午，它自己先替自己证明了一次。

结语

省钱的另一半，不在提示词里，在供给层里。

账单只记录花出去的钱，不记录被浪费的钱：死掉的渠道、冻结的预扣、重跑的任务、蹲守的晚上。把这半场的账管起来，不需要更聪明的模型——只需要把渠道当基础设施对待：体检、限速、留痕、备胎。

顺带一提：一整套做下来，你会发现最省钱的习惯其实是——让失败尽快地、安静地失败，然后换条路继续走。
